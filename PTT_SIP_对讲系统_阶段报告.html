1. 项目背景与目标

本项目面向电池供电的 4G 对讲设备，设备以“组”为单位通信。同一组内同一时间只允许一个设备讲话，其他设备处于监听状态。讲话设备按下讲话键后先向服务器申请讲话权，服务器批准后才发送音频。所有音频经过服务器转发，客户端之间不直接传输媒体。

  1. 使用纯 C 实现不依赖第三方 SIP/RTP 库的可运行原型。
  2. 在 WSL 上模拟三个客户端，在 ARM64 ECS 上运行服务端。
  3. 验证注册、入组、抢麦、释放讲话权和组内一对多 RTP 转发。
  4. 模拟每秒 40 个 Opus RTP 包，并统计毫秒级端到端延时。
  5. 解决 WSL/NAT 场景下服务器向错误 RTP 地址转发的问题。
  6. 将 ECS 服务端改为 systemd 自启动，并支持自动编译和自动重启。

2. 需求与设计

2.1 业务需求

  • 三个客户端加入同一个群组，例如 group_01。
  • 任意客户端输入 talk 申请讲话权，输入 release 释放讲话权。
  • 同一组只有一个讲话者，其他客户端只能监听。
  • 讲话者异常退出或超时后，服务器自动释放讲话权。
  • 所有 RTP 音频经过 ECS 服务器转发，客户端拒绝非服务器来源的 RTP。

2.2 协议分工

协议/消息用途
SIP REGISTER客户端注册并上报 RTP 接收端口
SIP INVITE加入指定群组
SIP MESSAGE / PTT-REQUEST申请讲话权
SIP MESSAGE / PTT-RELEASE释放讲话权
PTT-LISTEN / PTT-IDLE服务器通知组成员进入监听或空闲状态
RTP/UDP承载 Opus 音频数据和发送时间戳
client_001 -- SIP REGISTER/INVITE/MESSAGE --+\nclient_002 -- SIP REGISTER/INVITE/MESSAGE --+--> ECS SIP :5060\nclient_003 -- SIP REGISTER/INVITE/MESSAGE --+\n\n讲话客户端 -- RTP/UDP --> ECS RTP :40000\n                         ECS 转发 --> 同组其他客户端

服务器为每个 group_id 保存讲话权状态：FREE、OWNED_BY_CLIENT。只有收到 GRANTED 后客户端才发送 RTP，其他申请返回 BUSY。

3. 音频、带宽与功耗考虑

  • 目标格式：单声道 Opus，目标码率 16 kbit/s。
  • 包率：40 包/秒，每包 25 ms 音频。
  • 模拟 payload：约 50 字节/包；RTP 时间戳每包增加 1200（48 kHz）。
  • 空闲监听状态 RTP NAT 保活间隔：10 秒。
50 字节 × 40 = 2000 字节/秒 = 16.00 kbit/s\nRTP 扩展约 24 字节 + UDP 8 字节 + IPv4 20 字节\n总计约 102 字节/包 × 40 = 32.64 kbit/s\n单向媒体流约 14.01 MiB/小时

三人组一人讲话、两人监听时，讲话端上行约 32.64 kbit/s，每个监听端下行约 32.64 kbit/s，ECS 出口合计约 65.28 kbit/s。当前 PC 原型模拟 Opus 编码后的包长和二进制内容，尚未执行真实 PCM 到 Opus 的编码。

4. 延时统计方案

讲话端在 RTP 扩展头中写入 64 位 Unix 毫秒发送时间戳，服务器转发时不修改该字段，监听端按照“接收时间戳 - 发送时间戳”计算单向延时，每秒输出一次统计。

[client_002] [rx/1s] via=server packets=40 opus_payload=2000 bytes delay_ms avg=0.5 min=0 max=1 missing_timestamp=0

真实不同设备之间测量前需要 NTP 或网络授时，否则结果会混入发送端与接收端的时钟偏差。WSL 客户端共用同一台 PC 时钟，适合当前原型验证。

5. NAT/RTP 转发问题与修复

原始实现使用 SIP/SDP 中声明的 198.18.0.1:20002 等地址作为监听端点。该地址对 ECS 不可达，虽然服务器打印 recipients=2，但监听端收不到数据。

修复方案是客户端使用 RTP socket 发送 payload type 为 126 的 Keepalive，服务器根据实际 UDP 源地址和 SSRC 学习客户端真实公网 RTP endpoint。Keepalive 加入群组后立即发送，空闲时每 10 秒发送一次，讲话时由正常 RTP 包维持 NAT 映射。Keepalive 只用于学习地址，不转发。

7. ECS 自启动和自动部署

当前 ECS 工作目录为 /root/master，服务端使用 UDP 5060（SIP）和 UDP 40000（RTP）。systemd 单元每 30 秒检查一次 include/、src/ 和构建脚本的摘要。新代码连续两次检测一致后自动使用 ECS 本机 GCC 编译；编译成功则停止旧服务并启动新服务，编译失败则保留旧版本。

检查项当前结果
systemctl is-enabled ptt-server-autodeploy.serviceenabled
systemctl is-active ptt-server-autodeploy.serviceactive
ptt_server正在运行
UDP 5060 / UDP 40000正在监听

查看日志：

systemctl status ptt-server-autodeploy.service\njournalctl -u ptt-server-autodeploy.service -f -o cat\ntail -F /root/master/logs/server.log\ntail -F /root/master/logs/auto_deploy.log

8. 测试过程和结果

8.1 本地回归

通过 scripts/run_demo.sh 启动本地服务端和三个客户端，验证了注册、入组、client_001 抢麦、client_002 申请时返回 BUSY、服务器转发给两个监听端以及释放讲话权等流程。

8.2 ECS 公网测试

三个 WSL 客户端连接 ECS 公网地址 123.57.79.87。client_001 输入 talk 后，服务端显示 recipients=2，client_002 已观察到：

[client_002] [rx/1s] via=server packets=41 opus_payload=2050 bytes delay_ms avg=6.8 min=6 max=7 missing_timestamp=0\n[client_002] [rx/1s] via=server packets=40 opus_payload=2000 bytes delay_ms avg=6.7 min=6 max=7 missing_timestamp=0\n[client_002] [rx/1s] via=server packets=41 opus_payload=2050 bytes delay_ms avg=6.9 min=6 max=11 missing_timestamp=0\n[client_002] <- PTT-IDLE previous_speaker=client_001, state=IDLE
  • packets=40/41：符合每秒 40 包，41 包是统计窗口边界和调度造成的正常现象。
  • opus_payload=2000/2050：每包约 50 字节，符合模拟参数。
  • 平均延时约 6.7~6.9 ms，最大延时大部分为 7~8 ms，偶发 11 ms。
  • missing_timestamp=0：时间戳完整。
  • PTT-IDLE：讲话结束和状态广播正常。

阶段验收结论：PC/WSL 客户端、ECS ARM64 服务端、SIP 控制、抢麦、RTP 转发、NAT endpoint 学习、延时统计和 ECS 自启动链路已打通。

9. 当前限制与风险

  1. 当前没有真实 PCM 到 Opus 的编码，音频 payload 仍为模拟二进制数据。
  2. SIP 只实现当前场景所需子集，尚未实现完整事务重传和严格状态机。
  3. 尚未加入 SIP Digest 鉴权、TLS、SRTP、用户权限和设备权限管理。
  4. 尚未实现丢包重传、抖动缓冲和音频 PLC。
  5. 公网部署必须正确开放 UDP 5060 和 UDP 40000 安全组/防火墙规则。
  6. 真实 4G 设备之间进行单向延时测量前必须统一时钟。
  7. Keepalive 为 10 秒，最终间隔需要结合移远模组的实际电流和 NAT 超时测量。

10. 下一阶段计划

  1. 接入麦克风采集和真实 Opus 编码，替换模拟 payload。
  2. 确认具体移远型号，以及采用 OpenCPU 还是外部 MCU + AT Socket 方案。
  3. 替换 Socket、定时器、GPIO 按键、音频采集和播放适配层。
  4. 增加网络断线重连、注册刷新、弱信号和服务器重启恢复测试。
  5. 测量空闲、监听、讲话三种状态的 4G 电流，优化保活和休眠策略。
  6. 增加 Digest 鉴权、设备身份校验、群组权限、TLS/SRTP 和 RTP 注入防护。

11. 阶段结论

本阶段已经完成一个纯 C 的 SIP/RTP 组呼原型，并在 WSL 三客户端和 ARM64 ECS 环境完成公网链路验证。当前系统能够实现：

客户端注册 -> 加入群组 -> 申请讲话权 -> 服务器仲裁\n-> 讲话端发送 RTP -> ECS 一对多转发\n-> 监听端接收并统计延时 -> 释放讲话权

当前实测监听端平均延时约 7 ms，ECS 服务端 UDP 5060/40000 正常监听，自动部署服务为 enabled/active。下一阶段工作的核心是接入真实音频、完成移远模组适配、进行功耗和可靠性测试，并完成生产级安全加固。
