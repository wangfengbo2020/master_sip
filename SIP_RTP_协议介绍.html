SIP 与 RTP 协议介绍

面向 4G PTT 集群对讲系统 · 版本 1.0 · 2026-10-08

一句话理解：SIP 负责“谁加入、谁讲话、什么时候停止”等控制；RTP 负责持续传输 Opus 音频。SIP 类似呼叫调度员，RTP 类似真正承载声音的运输通道。
目录： 总体概念 SIP RTP PTT流程 端口与NAT 音频与带宽 时延与缓存 安全加密 低功耗

1. SIP 与 RTP 的总体关系

SIP：信令控制平面

完成注册、入组、抢麦、释放讲话权和状态通知。SIP 消息通常是可读文本，当前项目通过 UDP 传输。

控制数据 数据量小，可靠性和状态一致性重要。

RTP：实时媒体平面

承载 Opus 编码后的音频包，包含序号、时间戳、SSRC 和 Payload Type。当前项目通过 UDP 传输。

音频数据 数据连续，低延时比单包可靠性更重要。

比较项SIPRTP
主要职责会话、设备、群组和讲话权控制实时传输音频
当前传输层UDPUDP
数据形式文本报文二进制报文
数据频率状态变化时发送讲话期间约 40 包/秒
丢包影响可能造成状态不一致，需要应答和重传通常表现为短促音频缺失，不宜等待长时间重传
是否直接携带声音否是，承载 Opus payload

2. SIP 协议介绍

SIP（Session Initiation Protocol，会话初始协议）是应用层信令协议。标准 SIP 可用于建立、修改和结束语音或视频会话；在本项目中，仅实现 PTT 场景需要的轻量子集。

2.1 当前项目使用的 SIP 消息

消息方向作用
REGISTER客户端 → 服务端设备注册，提交设备 ID 和本地 RTP 接收端口
INVITE客户端 → 服务端加入指定群组，例如 group_01
ACK客户端 → 服务端确认 INVITE 的成功响应
MESSAGE / PTT-REQUEST客户端 → 服务端申请讲话权
MESSAGE / PTT-RELEASE客户端 → 服务端释放讲话权
MESSAGE / PTT-LISTEN服务端 → 监听端通知某个客户端开始讲话
MESSAGE / PTT-IDLE服务端 → 监听端通知讲话结束，恢复空闲状态
BYE客户端 → 服务端退出群组和结束当前会话

2.2 简化的抢麦报文示例

MESSAGE sip:group-group_01@123.57.79.87 SIP/2.0
From: <sip:client_001@device>
To: <sip:group-group_01@server>
X-Device-ID: client_001
X-Group-ID: group_01
Content-Type: application/x-ptt
Content-Length: 11

PTT-REQUEST

服务端如果发现群组当前无人讲话，则返回 X-PTT-Result: GRANTED；如果已有讲话者，则返回 BUSY 和当前讲话者 ID。

当前原型限制：尚未实现完整 SIP UDP 事务重传。服务端的 PTT-LISTEN 或 PTT-IDLE 如果丢失，客户端可能暂时停留在错误状态。生产版本应保存待确认事务，根据 Call-ID/CSeq 等待 200 OK，超时后重传，并让客户端能够幂等处理重复消息。

3. RTP 协议介绍

RTP（Real-time Transport Protocol，实时传输协议）用于在 IP 网络中传送实时音频或视频。RTP 通常运行在 UDP 之上，本身不保证报文一定到达、不保证按序到达，也不负责重传。

3.1 RTP 头部中的关键字段

字段作用本项目用途
Payload Type说明负载类型111 表示 Opus；126 用作 NAT Keepalive
Sequence Number每发一个包递增，用于发现丢包和乱序16 位，40 包/秒时约 27 分钟回绕一次
Timestamp表示音频采样时间位置按 48 kHz 时钟，每 25 ms 增加 1200
SSRC标识一个 RTP 数据源帮助服务器识别设备并学习 NAT 后的实际端点
扩展头携带业务自定义信息当前携带 64 位 Unix 毫秒发送时间戳
Payload真正的媒体数据当前为约 50 字节的模拟 Opus 二进制负载
RTP packet
┌──────────── 标准 RTP 头：12 bytes ────────────┐
│ V/PT │ Sequence │ Timestamp │ SSRC            │
├──────────── 项目扩展头：12 bytes ─────────────┤
│ Profile/Length │ Unix send_time_ms：8 bytes   │
├──────────── Opus payload：约 50 bytes ────────┤
│ 编码后的音频数据                              │
└───────────────────────────────────────────────┘

RTCP 通常与 RTP 配套，用于上报丢包率、抖动和往返时间。当前项目没有实现 RTCP，而是由监听端每秒直接统计收到的 RTP 包数和单向延时。

5. 端口、IP 与 NAT

5.1 当前测试端口

节点SIP 本地端口RTP 本地端口
client_0011507120001
client_0021507220002
client_0031507320003
ECS 服务端506040000

三个客户端运行在同一个 WSL IP 上，因此 SIP 和 RTP 本地端口都必须不同。UDP 数据先依据“目标 IP + 目标端口”交给进程，RTP 的 SSRC 只有在进程收到数据后才能解析，不能替代端口区分。

三台独立的真实设备具有不同本地 IP 时，可以都使用相同的本地 RTP 端口，例如各自使用 20001。经过 4G 运营商 NAT 后，服务端以实际观察到的公网 IP:port 为准。

5.2 NAT 地址学习

客户端入组后从自己的 RTP socket 发送 Keepalive。服务端根据该 UDP 包的源地址和 SSRC 更新实际 RTP 返回地址。讲话期间，正常 RTP 包继续维持 NAT 映射。

SIP 报文中声明的 WSL 私网地址可能对 ECS 不可达，因此服务端不能只相信报文里的地址，必须使用实际收到数据包的公网源地址。当前 Keepalive 间隔为 10 秒，最终产品需要根据运营商 NAT 超时时间和实测电流调整。

5.3 群组是否需要独立端口

不需要为每个群组分配独立的 SIP 和 RTP 端口。群组由 group_id、设备身份和服务端群组状态表区分，端口只用于把 UDP 数据交给 SIP 服务或 RTP 服务。

group_01 ─┐
group_02 ─┼── SIP → ECS UDP 5060
group_03 ─┘

所有讲话设备 ─── RTP → ECS UDP 40000
服务端根据设备会话、SSRC 和 group_id 转发到正确群组

生产环境建议采用以下分配方式：

端口类型由谁分配建议
服务端 SIP 端口平台运维或服务端配置固定端口；常见为 5060，使用 SIP/TLS 时常见为 5061
服务端 RTP 端口媒体服务配置或媒体调度器当前可以固定使用 40000；扩容时由服务端从端口池或不同媒体节点分配
客户端本地端口设备操作系统、模组 Socket 层或客户端程序真实设备建议动态分配；同一 IP 上的多个客户端必须避免冲突
NAT 后的公网端口4G 运营商、路由器或 NAT 网关设备无法指定，服务端通过实际收到的数据包和 Keepalive 学习
群组 ID业务平台或设备管理后台使用逻辑 ID 管理，不与 UDP 端口绑定

如果未来并发量很大，可以把不同群组调度到不同 RTP 端口或不同媒体服务器，但这是扩容和负载均衡策略，不是 SIP/RTP 协议要求。具体端口应由服务端在入组响应或 SDP 中下发，客户端不应自行决定或为每个群组硬编码端口。

端口不能作为群组隔离或安全机制。即使所有群组共用同一个 RTP 端口，也必须根据已认证的设备身份、会话、讲话权和群组权限决定是否接收和转发数据。

7. 时延、缓存和丢包

7.1 延时统计

讲话端把发送时刻写入 RTP 扩展头，服务端保持报文不变地转发，监听端使用“接收时间减发送时间”计算端到端单向延时，并每秒输出平均值、最小值和最大值。

[client_002] [rx/1s] via=server packets=40 opus_payload=2000 bytes
delay_ms avg=5.4 min=5 max=6 missing_timestamp=0

不同真实设备测量单向延时前必须进行时钟同步，否则结果会包含两台设备的时钟误差。

7.2 服务端是否缓存音频

当前服务端没有应用层音频缓存。它每次读取一个 RTP 包，完成校验后立即调用 sendto() 转发，然后复用同一个临时缓冲区。不存在录音、历史回放、多包排队、重排序或媒体重传。

  • 优点：内存占用小、处理路径短、转发延时低。
  • 限制：UDP 包丢失后不会恢复；乱序和网络抖动需要监听端处理。

真实音频播放端建议从 3～4 个包的抖动缓冲开始，即约 75～100 ms，再根据4G网络测试结果做自适应调整。抖动缓冲应主要放在客户端，而不是服务端。

8. 鉴权与加密建议

8.1 SIP 信令

生产版本至少需要设备身份认证、消息完整性校验和重放保护。标准方案可以使用 SIP over TLS；低功耗 UDP 方案可以使用每设备独立 PSK，并为消息增加 HMAC-SHA256、时间戳和单调递增计数器。

8.2 RTP 音频

推荐采用 SRTP，并优先选择 AES-128-GCM。服务端可以终止上行 SRTP，验证并解密后，再使用各监听设备的独立会话密钥重新加密。这样便于单设备撤销、密钥轮换和权限管理。

  • 不要只加密而不认证；应使用 AES-GCM 或 ChaCha20-Poly1305 等 AEAD 算法。
  • 同一个密钥下绝不能重复使用 Nonce。不能只使用会回绕的16位 RTP 序号生成 Nonce。
  • 设备长期密钥不得硬编码在公共固件中，应使用安全存储并为每台设备配置独立密钥。
  • 不要自行实现 AES/GCM 算法，优先使用移远 SDK、芯片硬件加密接口或经过审计的密码库。

使用16字节认证标签时，每路增加约 5.12 kbit/s，即约 2.20 MiB/小时，当前单向媒体带宽将从约 32.64 kbit/s 增加到约 37.76 kbit/s。

9. 4G 设备低功耗重点

  1. 无线状态优先：LTE 发射和 RRC 保持的功耗通常远高于 SIP/RTP 解析及一次 AES 运算。
  2. 控制 Keepalive：过于频繁的 UDP 保活可能让模组长期不能进入低功耗状态。需要实测不同运营商的 NAT 映射保持时间。
  3. 监听可达性与休眠取舍：设备越深度休眠，越难及时收到服务器的 PTT-LISTEN；需要在呼入时延和电池寿命之间确定产品指标。
  4. 优先硬件加密：有 AES 加速时优先 AES-GCM；无 AES 加速时可测试 ChaCha20-Poly1305 的执行时间和电流。
  5. 避免无意义重传音频：实时对讲中，过期语音包通常直接丢弃比延迟播放更合理；控制信令则必须确认和重传。

11. 总结

SIP 和 RTP 在对讲系统中分工清晰：SIP 保证群组和讲话权状态正确，RTP 以尽可能低的延时传送 Opus 音频。当前原型已经验证“三客户端注册入组、单讲话者仲裁、ECS 一对多转发、毫秒级延时统计和 NAT 端点学习”。下一阶段重点是信令可靠性、真实 Opus 音频、客户端抖动缓冲、加密鉴权以及移远模组功耗测试。
